## 1. What this is

One game, presented as a game. The page's own description says so plainly: a
game built on real simulation runs from this library, indicative of how the
library is meant to be used in more sophisticated form. No prototype language
and no apology. The page carries a named owner and ends with the off-ramp:
this is one hand-built scenario; the library is how you build your own.

The player is inserted into a society where humans are losing. The opening of
a run is watching the drift before any decision is asked. At a small number of
intervention windows the run pauses; the player spends from resources that
depend on how the run is going; the run continues down the chosen branch. Past
the knee, a window can open onto an empty tray: the capacity to act is gone.
That moment is the game's reason to exist.

## 2. Decisions (2026-07-31)

- **Game frame, unapologetic.** Decision. The fiction is load-bearing: a
  named, dated scenario bounds the loss the way a research dashboard cannot.
- **One scenario, drift already underway, shown before first input.** Decision.
- **Intervention windows, not free-running controls.** Decision. Three windows
  in v1.
- **Resources typed by ledger.** Decision. The player's capacity to act at a
  window is read from the current human shares of the conserved ledgers.
  Economic interventions cost wealth capacity; political interventions cost
  authority capacity. There is no single pooled currency.
- **Costs are in-model ledger debits.** Decision. Choosing an intervention
  transfers ledger mass at the window tick inside the dynamics. Scarcity is a
  fact of the run, not a rule of the interface.
- **Fog of war is cut from the game.** Decision. The scoreboard always shows
  true shares. The perceived-share instrument remains available to the
  research side independently of this page.
- **Debrief shows the tree.** Decision. After a run: the path walked, the
  branches not taken, and a solution table over all paths published by us on
  day one. Seed spread renders as separate unsmoothed lines, never a smoothed
  band. Exported images carry scenario, version, date, and seed count in the
  pixels.
- **Extending ledger_society for this is a deliberate exception** to the
  observability-first sequencing in the active intent. Decision, dated here.
  The extension is bounded to intervention events and their debits.

## 3. Design conjectures carried from the review session

Untested, held as design guidance:

- Every affordance is a claim: the deck of available interventions, the cost
  structure, and the picture each assert something below the level of
  argument. The debrief therefore lists the interventions that were considered
  and cut, with the reason each was cut.
- A win reached easily teaches that the problem is easy. The scenario is
  tuned so that early, well-chosen commitment is the only reliable path, and
  the solution table makes the narrowness visible.
- The modal visitor stays under two minutes and leaves with one image. The
  opening drift sequence and the share picture are designed as that image.
- A deliberately losing scenario needs the loss bounded by fiction and the
  exit handled inside the losing screen, in one sentence, written before code.

## 4. Mechanism

**A branch is a full run.** Each path through the windows is one complete
engine run from t=0 with a fixed intervention schedule. Determinism with a
shared seed makes prefixes identical, so no state-resume machinery is needed;
the redundant prefix compute is trivial at this scale.

**The tree is generated by affordability.** The generator runs a branch, reads
the human ledger shares at the next window tick, prices the deck against
them, and recurses over the affordable subsets. Affordability is decided by
the engine at generation time; the browser walks a finished tree and computes
nothing. The empty tray late in a losing run is a property of the artifact,
not interface logic.

**Interventions are schedule-gated transforms.** Activation at a window tick
uses the existing onset machinery with the branch's schedule closed over;
no data-dependent Python control flow. The debit is a conserved transfer on
the priced ledger at the same tick. Each intervention needs mechanically
distinct costs and effects for the typing to be real; confirming this against
current ledger_society dynamics is the first task below.

**Sizing, napkin.** Three windows, affordability-bounded branching of four to
six choices early and fewer late: roughly 100–300 paths. Eight seeds per path
for the outcome distribution: 1,000–2,500 runs, vmap-batched, minutes.
Playback payloads per branch reuse the contract-v1.1 pruning; the tree
artifact stays in the tens of megabytes at most, fetched lazily per branch.

## 5. Phases (G0–G3 built 2026-07-31; G4 is the web side)

- **G0 — the deck is authored, not discovered.** The five cards are a
  game-design decision; the engine read was reconnaissance for their build
  cost. The realization (decision, 2026-07-31): **two currencies, not
  three** — there is no authority ledger in the model; attention and ballots
  are per-row conserved shares that cannot be globally spent. Economic cards
  are floored on the human wealth share; political cards debit the existing
  `enforcement` stock, the bounded institutional-capacity quantity that lobby
  pressure erodes and repair replenishes — so the political budget is
  state-dependent with zero invented mechanics. The deck
  (experiments/gd_game/config.py, all prices tuned-for-legibility, probed
  2026-07-31): AI wealth levy (conserving transfer; enforcement 0.25),
  ballot-lottery sortition (the existing mechanism on `delegation`;
  enforcement 0.45), reach cap (a channel property — `reach_cut` in
  ledger_society config, since a cap written in the mechanism slot would be
  overwritten before the kernel reads it; enforcement 0.35), attention
  campaign (one-shot allocation shift, wealth floor 0.30), fund repair
  (wealth drip into the declared `intervention_spend` sink buying bounded
  enforcement uplift; wealth floor 0.20). Cut cards ship in the manifest with
  reasons: channel seal (subsumed — the cap at 1.0), disclosure (not
  modeled; strongest future mechanic), reserve (cannot score inside one run).
- **G1 — intervention events in ledger_society.** Built: one composed
  transform (`mechanisms/interventions.py`) carries a branch's whole plan —
  the cards share write fields, so separate mechanisms would break the
  same-family disjoint-writes rule. An empty plan is a bit-exact identity
  (ladder rung), the fifth sink extends the conservation rung, `reach_cut=0`
  is bit-identical, and ASSUMPTIONS.md carries the dated entry.
- **G2 — the tree generator.** Built: `experiments/gd_game/` in the
  `_template` shape; every prefix is priced from its wait-completion run,
  waiting is always a legal move, affordability uses the median across the
  seed batch at the tick before each window. Committed expectations are
  ordering claims; the shrinking tray is a separately-labeled DESIGN gate
  whose prices may be revised under their declared typing. Probed arc on the
  wait path: enforcement 0.666/0.320/0.231, tray 5 -> 2 -> 0 across windows
  100/200/300 — the empty final tray is a property of the artifact.
- **G3 — the tree artifact.** Built: `tree.json` (O0-shaped metrics with
  kind + version + definition hash; nodes carry window state, resources and
  the affordable set; checksums written last) + `runs/p-*.json`
  contract-v1.1 payloads whose system DAG includes the branch's intervention
  transforms. Schema validated on write, shipped alongside for eq-network's
  ajv.
- **G4 — the web game.** The page walks the tree behind the existing engine
  seam of the playground app: watch, window, choose, outcome, debrief. Scene
  animation uses the traced flow-target series. Handoff to Markov is the tree
  schema plus this doc. The client should consume a *branch provider*
  interface (node + affordable set + branch payload) so a future live-engine
  endpoint is a config change, not a rewrite — the tree generator is that
  engine's batch mode, and it remains the only producer of the solution
  table either way.

## 6. What a critic should press on

The debit mechanics will be tuned until the game is playable, which is
exactly the tuned-for-legibility risk this repo documents elsewhere; every
price and window tick must carry its type, and any dynamic added because the
game needed it must say so wherever the effect is discussed. The claim that
windows and shrinking affordability produce a felt lesson about lock-in is a
design conjecture with no user evidence; the first real players may
experience a menu, not a moment. The review session that shaped this plan was
a simulation; nothing it produced is evidence about players or readers. One
scenario invites overfitting the model to one story; the register models, not
this game, remain the load-bearing research objects. And the page may simply
go unvisited, in which case the engine work must justify itself — G1's
intervention events and G2's tree sweep are designed to stand as research
instruments with or without the game in front of them.
